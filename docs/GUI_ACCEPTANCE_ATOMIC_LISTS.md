# 原子列表迁移 · 真机 GUI 验收清单

日期：2026-10-10。第 14 节（`ADVERSARIAL_REVIEW_2026-10-01.md`）把七个列表全部接入原子路径后，有两项只有真机能验证。本清单供人工执行，每项都写明了通过标准与失败时的含义。

跑之前先 `npm run build`，然后正常启动应用（不要用探针脚本——本清单验的就是人操作时的行为）。

store 目录：`%APPDATA%\<productName>\lingyu_store\`（`src/main/index.ts:262`）。每项验收前后都可以直接看这里的 `<key>.json`，这是判断"到底存了什么"的唯一凭据。

## A. 两个窗口同时新增（验合并不丢条目）

需要灵动岛窗口与独立工作台窗口同时可见。打开工作台：灵动岛 expanded 态点入口，或设置里切到独立窗口模式。

| # | 操作 | 通过标准 |
| --- | --- | --- |
| A1 | 工作台系统工具拖一个 .exe 进快捷启动；同时灵动岛总览页拖拽排序 | 两个操作都生效，`app-shortcuts.json` 条目数等于拖入的数，顺序等于你最后看到的那样 |
| A2 | 工作台设置-休息提醒改一个条目的名称；同时灵动岛触发一次提醒或等一轮 | 名称不被冲掉。重点看 `break-reminder-items.json` 里那条的 `name` 与 `intervalMinutes` |
| A3 | 工作台剪贴板历史页追加（复制一段文本）；同时设置页点清空历史记录 | 见下方说明，这一项允许两种结果 |
| A4 | 灵动岛拖文件到暂存架；同时工作台暂存架也拖一个 | `shelf.json` 两个文件都在 |

A3 说明：清空走原子合并，语义是"删掉我读到时看到的全部条目，保留别人刚加的"。所以复制若发生在清空之前，它应当被删掉；若发生在清空之后（采集器并发追加），它应当保留。两种都对。失败的表现是：清空后历史里仍留着清空前就有的旧条目（说明整表覆盖没修掉），或者明明刚复制的内容被无声吞掉且设置页显示清空成功。

## B. 拖拽排序与并发新增同时发生（第 13 节的遗留项）

这一项从 url-favorites 迁移起就标记为未实测，现在是最后一次确认的机会。

| # | 操作 | 通过标准 |
| --- | --- | --- |
| B1 | 两个窗口都打开 url-favorites；窗口 1 拖拽排序，窗口 2 立刻新增一条 | 不丢条目。被并发新增的那条会按 current 顺序补到末尾，它自己的相对位置可能移动，这是第 13 节写明的预期，不算失败 |
| B2 | 灵动岛总览页拖拽快捷启动排序，同时工作台系统工具页拖入一个新应用 | 同上：不丢是硬标准，末端位置是预期 |

唯一算失败的情况：条目消失，或顺序在你没有 drag 的情况下被大幅重排（说明 after 顺序没被尊重）。

## C. 老用户旧格式数据升级（验迁移真的会发生）

这一项验的是本轮修的两个回归。先在备份目录里留一份 `lingyu_store` 再动手。

手动造旧数据：退出应用，按下面格式写文件，再启动。

```json
// app-shortcuts.json —— 旧版用 Date.now() + Math.random()，id 是小数
[{"id":1770000000000.4141,"name":"记事本","path":"C:\\Windows\\System32\\notepad.exe","iconBase64":null}]
```

```json
// break-reminder-items.json —— 旧版 id 是 string
[{"id":"1770000000000-a1b2c3","name":"喝水","intervalMinutes":60,"enabled":true}]
```

| # | 操作 | 通过标准 |
| --- | --- | --- |
| C1 | 用上面的 app-shortcuts.json 启动，打开工作台系统工具页 | 条目显示出来，不是空列表。文件里的 id 变成 1770000000000 这样的整数 |
| C2 | 在 C1 的基础上拖入一个新应用 | 新条目与旧条目都在。这一项验的是第一次编辑能落盘，修之前会静默失败 |
| C3 | 用上面的 break-reminder-items.json 启动，打开设置-休息提醒 | 条目显示出来，名称是喝水，60 分钟。文件里的 id 变成整数 |
| C4 | 在 C3 的基础上改一下间隔分钟数 | 改动保存成功。关掉设置页再打开，改动还在 |
| C5 | 删除 C3 里最后一条提醒 | 列表保持为空，显示暂无提醒事项空状态，不自动填回默认两条 |

C5 是最容易回归的一项：它验的是只在 store 文件不存在时播种默认值。如果删空后默认提醒立刻回来，就是这个 bug 复发了。

## D. 冲突反馈（验 UX 没被迁移破坏）

原子合并遇冲突时会弹 `storageSync.*` 的双语通知。这一项不需要真构造冲突（很难），只确认通知本身中英文都正常：切换应用语言到 English，再触发一次 A1，看提示文案。
